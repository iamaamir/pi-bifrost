# Acceptance report comments

The top-level deterministic `npm run acceptance` invocation in GitHub Actions writes `ci-report.md` and sanitized `report-data.json`. It exports both exact paths through `GITHUB_OUTPUT` and appends the Markdown to `GITHUB_STEP_SUMMARY`. That step summary is provisional because the workflow conclusion is not known yet. It can show `BLOCKED` when required checks fail; an otherwise passing run remains incomplete until the workflow reports success. The `Verification` workflow uploads Markdown and publisher JSON as separate artifacts; each artifact name includes the PR head SHA, workflow run ID, and run attempt.

The separate `Acceptance report` workflow runs from the trusted default branch, checks the completed run and current PR head through GitHub's API, then updates one marker-owned comment. It never checks out the PR head or executes the artifact. The first comment is published only after `.github/workflows/acceptance-report.yml` has reached the repository's default branch; GitHub requires a `workflow_run` workflow file to exist there before it triggers.

The publisher looks up only the JSON report artifact for the exact run and validates its SHA/run/attempt-bound name and run metadata before downloading by artifact ID. It does not select artifacts by a filename glob. Artifact metadata must fit within 1 MiB, and the downloaded directory may contain only `report-data.json` (optionally under the generated run directory); JSON is limited to 512 KiB. The publisher never downloads the separate Markdown artifact; it renders the final report from validated JSON using trusted code. Missing, malformed, stale, cancelled, or failed evidence produces a blocked or incomplete report.

The report puts its scope beside the confidence line and shows a compact table for the seven release gates. Action items and supporting details sit inside a collapsed section. `VERIFIED CHECKS` requires all seven gates, all required cases, and stable source provenance to pass. It describes checks for one candidate; product-requirement coverage remains partial.

The pull request controls the workflow producer and test code that create the report evidence. Review changes to those files and their assertions before relying on the result; the publisher checks report provenance and PR association but does not independently execute or prove the candidate's tests.
