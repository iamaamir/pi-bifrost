    01 / Pi-native virtual model

    Auto routes inside Pi, not through a proxy.

    Run /model in Pi and select bifrost/auto. For each new user turn, Bifrost chooses from your configured models. Pi dispatches the physical model and records which model answered.

    Tool continuations stay with that physical model. Selecting Auto is deliberate; normal routing instead sets Pi's active physical model before generation.

    How Auto works in Pi

    02 / Persistent failure circuit

    Failed model? Skip it on the next turn.

    After repeated failures within your configured window, Bifrost opens that model's circuit. It excludes the model from new routing decisions and can choose another healthy model from your list.

    Reliability state survives a restart. Usage or billing rejections pause the configured Pi provider in Auto and physical routing by default. Set reliability.allowanceCooldownScope to model to limit those pauses to one model. A generic HTTP 429 pauses the provider briefly. Auto can make one alternate attempt only after Pi proves the failed turn was empty and safe to continue. Set reliability.retryOnAllowanceExhausted: false to stop the retry but keep the pause. Read the reliability guide for scope and timing details.

    This scene shows the third failure with the default threshold, then a separate new user turn. See reliability rules.

    03 / Classifier choice

    Choose who decides the group.

    Classification is enabled by default. Run /bifrost classifier to choose a Pi chat model, TypeSafe/Jev, or Pi's native classifier API. On a local-cache miss, the active classifier can receive the current prompt. Pi-native appears only on hosts that support classification. Run /bifrost classifier off to use rules and the default group without the extra classification call.

    A classifier chooses a group such as quick or frontier. It does not choose your provider model. Your pools, reliability circuit, and selection strategy make that decision.

    An omitted backend can be detected from credentials; an explicit backend overrides detection. Classifier requests can incur usage. Compare backends.

    04 / Default route

    Pi switches models before the prompt.

    On a fresh install, routing is on by default. Bifrost builds model lists from Pi's catalog and saves a small project .pi/bifrost.json in the background. An empty {} configuration does not block setup. A configuration with one setting, a route file, or an explicit routing setting does. This save sends no probes and writes no prompts or secrets. If a safe save fails, routing continues in memory and Bifrost warns. bifrost/auto remains a separate opt-in. Use /bifrost inspect or /bifrost debug to review lists and status.

    See the default route.

    05 / Setup

    Refresh or review model lists.

    First-use setup saves a minimal project config automatically when it is safe. Run /bifrost init to refresh the catalog or reconcile saved model lists. Init shows a short summary and asks once before it saves. The summary omits some model IDs and selection rules. Inspect and edit the saved config before a model answers when needed. Pass -f to probe models. Probes can use provider credits or reach rate limits.

    Read the init steps and probe limits.

    06 / Explicit routes

    Use rules, a direct model, or a tier prefix.

    Each rule in .pi/bifrost.json has a text pattern and a model value. Below, quick means “choose from the quick pool.” example/deep-model means “use this exact model,” without a tier strategy.

    {
  "rules": [
    { "pattern": "commit",
      "model": "quick" },
    { "pattern": "security audit",
      "model": "example/deep-model" }
  ]
}

    Replace example/deep-model with a model ID available in Pi. The commit rule can select quick if no earlier tier choice wins. To force quick for one unpinned turn, type quick commit the changes. Bifrost removes quick before the model sees it.

    07 / Your selection policy

    Pick how each group chooses a model.

    Set categoryStrategies in .pi/bifrost.json. This example makes the quick pool choose the healthy model with the lowest combined input and output price:

    {
  "categoryStrategies": {
    "quick": "cheapest"
  }
}

    Other choices include first, largest_context, and random. fastest uses list order, not live speed. Init can sort that list using one-time probe results. Open circuits are removed first.

    See every strategy and configuration example.

    08 / Check before sending

    Preview the actual model.

    Run /bifrost preview security audit this code in Pi. It shows the chosen tier, model, source, and exclusions without starting a generation turn or switching Pi's active model. An enabled classifier can receive the preview text and incur usage. Preview does not treat a leading tier name as an override. Pass --json before the prompt for a machine-readable report.

    Learn what preview does and does not run.

    09 / Manual control

    Pin, unpin, or switch routing off.

    Run /bifrost pin to keep the current physical model for this session. Even a tier prefix stays in the prompt while pinned. Run /bifrost unpin to resume routing. Selecting a physical model in Pi's /model picker also pins it.

    Run /bifrost off to stop routing, then /bifrost on to resume. On/off survives a restart; a pin does not. Pin or off while Auto is selected switches back to a physical model.

    See every control and Auto exit behavior.

    10 / Local classification cache

    Reuse a tier decision, not an answer.

    Run /bifrost cache stats to inspect stored tier decisions or /bifrost cache clear to empty them. Set cache.enabled to false in your existing config, then run /bifrost reload to disable classification-cache use. If no config exists, save starter pools with /bifrost init first and keep those pools when editing. This does not clear saved entries. Normalized prompt words can contain sensitive text. Bifrost never caches generated answers.

    Read cache storage and privacy details.

    11 / Inspect

    See status and local diagnostics.

    Run /bifrost debug to see effective routing settings and open-circuit count. To record local JSONL events, set "debug": { "enabled": true } in .pi/bifrost.json and run /bifrost reload. Normal traces omit raw prompt bodies.

    Set up local diagnostics.

    Routing stays bounded by configuration.

    Tier arrays define eligibility. Per-tier strategies choose among healthy candidates. Optional semantic judgment decides only which configured tier fits the prompt.

    .pi/bifrost.json 
    {
  "models": {
    "quick": ["provider/fast-model", "provider/backup-fast"],
    "general": ["provider/general-model"],
    "frontier": ["provider/frontier-model"]
  },
  "categoryStrategies": {
    "quick": "cheapest",
    "general": "first",
    "frontier": "largest_context"
  }
}

      pi install npm:pi-bifrost
    2. 02

      Save model groups (optional)

      This step is optional. Run it inside Pi to refresh the catalog and save model pools. It does not probe models by default. Pass -f to probe, which can incur provider usage or rate limits. Review the summary before confirming it.

      /bifrost init

    Classification is enabled by default, and the active classifier can receive the current prompt on a cache miss. Run /bifrost classifier off to use rules and the default tier without that extra call. This does not make generation local; the selected provider still receives the prompt. Selecting bifrost/auto in Pi's model picker is a separate opt-in for per-request dispatch.

    Four useful answers

    Detailed setup and reference material lives in the versioned guide.

    Do I need an LLM classifier?

    No. A tier name at the start of a message, regex rules, or the configured default can route without another model call. Prompt classifiers are optional when semantic tier judgment adds value. Choose a prompt, Pi-native, or TypeSafe backend.

    When should I avoid adaptive routing?

    Pin one exact model when a long session builds on the same context, prompt-cache locality matters, or switching would disrupt latency, billing, or workflow expectations. Adaptive routing trades continuity for per-turn task fit. It does not guarantee better results, lower cost, lower latency, or cache savings.

    Does routing affect provider prompt caching?

    It can. Treat every provider/model pair as an independent cache history. Returning to a model may reuse its longest still-valid prefix, while newer conversation content remains an uncached tail. Bifrost does not manage provider caches. Read the dedicated A → B → A and N-switch guide.

    What happens when a model fails?

    Bifrost records model failures and can stop using a model for a time. Usage or billing rejections pause the same configured Pi provider by default in Auto and physical routing. A generic HTTP 429 pauses that provider briefly. Auto can make one alternate attempt only after Pi proves the failure was empty and safe to continue. Pins do not bypass a provider pause.
