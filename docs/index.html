Bifrost

Automatically route each Pi prompt to a model based on task complexity, price, speed, or context length.

Get started →

What it does

Every prompt you type is different. Debugging a race condition needs a powerful model with deep reasoning. Formatting code or summarising a file doesn't — a cheap, fast model works fine.

Bifrost reads your prompt before it's sent, classifies it by complexity, and switches pi to the best model for that task. You never touch /model. The right model is already selected.

🧠 Prompt is classified

LLM or regex reads your prompt and assigns it to a tier — frontier for hard tasks, economical for simple ones, or any tier you define.

🎯 Best model is selected

Your chosen strategy picks the best model from the tier: cheapest, fastest, largest context, or random. Every decision uses metadata only — no API calls.

🔄 Model switches automatically

Before your prompt reaches the LLM, pi switches to the selected model. You just type. The model changes behind the scenes.

Why Bifrost

🔬 Never configure a dead model

Bifrost tests every model with a real request before writing your config. Models that fail, time out, or need API keys you don't have are excluded automatically.

⚡ Routing costs nothing

All 7 strategies use model metadata — token cost, context size — not API calls. Every routing decision is free. No tokens burned on the router itself.

📊 Debug any routing decision

JSONL trace logs which model was picked and why. Timestamps, classification source, tier, strategy. AI-parseable. If a surprise model fires, you can trace exactly why.

🎯 Pin models to prompts

Bind /commit to your best model and /explain to your cheapest. Regex rules assign specific models to specific prompts, bypassing tier selection entirely.

⚡ Override mid-sentence

Type !frontier debug this to force the expensive model for one message. No config edit, no unpin. The override is stripped before routing so the prompt is clean.

Privacy & behavior

Does the classifier see the full prompt?

Yes. The complete prompt text is sent to the classifier model to determine which tier fits. This is necessary for accurate routing — a classifier can't judge complexity from a summary.

Does classification send data to another provider?

Only if you enable the LLM classifier. The classifier model runs on a provider you choose in config — same as any other pi model. If you disable it or use regex-only routing, no prompt data leaves your machine beyond what pi already sends for normal chat.

Are prompts stored or logged?

Not by Bifrost. Prompt text is used only for in-memory classification and optional cache lookups (stored locally in .pi/bifrost-cache.jsonl as normalized fingerprints, not raw text). If debug logging is enabled, timings and routing decisions are written to .pi/bifrost-debug.jsonl, but prompt text is never logged.

What happens when classification fails?

The pipeline has four layers: direct bindings → cache → LLM classifier → regex fallback → default tier. If every layer fails, Bifrost doesn't route and pi uses its default model. A warning is shown. The classifier model errors (timeout, rate limit, unavailable) are caught individually — the next model in the list is tried.

How often does it pick an unsuitable model?

Uncommon in practice. The LLM classifier is configured with your tier names and picks the most fitting one. If it consistently misclassifies, adjust your config: tighten regex rules, add a direct binding, or pin a tier. The /bifrost preview command shows what would be picked before you send.

Are tool calls and conversation context considered?

Not yet. Each prompt is classified independently of conversation history. Tool call outputs and previous messages do not influence tier selection. This is a deliberate simplification — context-aware routing is planned for a future release, but it adds complexity and potential for unexpected model switches mid-conversation.

Config

Everything lives in .pi/bifrost.json. Editor autocomplete works in VS Code, Zed, Cursor.

Prefix any prompt with !tiername to force a tier for one message. Set "model": "provider/id" in a rule to bypass tier selection and route directly to a specific model.

{
  "enabled": true,
  "default": "economical",
  "strategy": "first",
  "categoryStrategies": { "economical": "cheapest" },
  "models": {
    "economical": [
      "opencode/deepseek-v4-flash-free",
      "lmstudio/openai/gpt-oss-20b"
    ],
    "frontier": [
      "opencode-go/glm-5.1",
      "opencode-go/grok-4.5"
    ]
  },
  "rules": [
    { "pattern": "\\b(debug|fix|implement)\\b", "model": "frontier" },
    { "pattern": "\\b(explain|format|hello)\\b", "model": "economical" }
  ],
  "classifier": {
    "enabled": true,
    "model": "opencode/mimo-v2.5-free"
  }
}

Classification takes ~2–500ms

Cache hits and regex matches resolve in ~1–2ms. LLM classification takes 100–500ms depending on model. Direct bindings cost nothing beyond a regex check. You only pay for classification if you enable the LLM classifier.

Works with any pi provider

No provider-specific logic. If pi can talk to a model, Bifrost can route to it. opencode, opencode-go, lmstudio, ollama, openai, anthropic, Google, custom providers — all supported.

What it doesn't do (yet)

No conversation context awareness — each prompt is classified independently. No per-user routing or team policies. No budget enforcement. These are planned for v0.3+. For now, the classifier is optional and can be disabled if every millisecond matters.

Troubleshooting

/bifrost preview <prompt> shows what would fire before you send it. /bifrost debug dumps loaded config and rules. /bifrost classifier off disables the LLM if it's misbehaving. Debug logs at .pi/bifrost-debug.jsonl capture every decision.
