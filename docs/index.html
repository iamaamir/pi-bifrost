One turn. Four clear decisions.

Bifrost separates the tier choice from exact-model selection. The classifier never receives authority to ignore your configured pool or strategy.

Tier
A named capability group.
Pool
Models allowed for that tier.
Strategy
How one healthy model is chosen.
Classifier
Optional tier judge, not model selector.
  1. 01

    Resolve a tier

    A tier prefix, cache hit, optional classifier, regex rule, or configured default resolves quick, general, frontier, or your own tier.

  2. 02

    Load your model pool

    Only models you placed in that tier become candidates. Add or remove provider/model IDs directly in configuration.

  3. 03

    Filter unhealthy candidates

    Persistent reliability circuits exclude repeatedly failing models before selection and later permit controlled recovery.

  4. 04

    Apply your tier strategy

    Choose list order, cost, context window, probe-sorted speed, or explicit random selection. Bifrost then activates Pi's actual model before generation.

Routing stays bounded by configuration.

Tier arrays define eligibility. Per-tier strategies choose among healthy candidates. Optional semantic judgment decides only which configured tier fits the prompt.

.pi/bifrost.json 
{
  "models": {
    "quick": ["provider/fast-model", "provider/backup-fast"],
    "general": ["provider/general-model"],
    "frontier": ["provider/frontier-model"]
  },
  "categoryStrategies": {
    "quick": "cheapest",
    "general": "first",
    "frontier": "largest_context"
  }
}

Optional classifier backend

Jev judges the tier. Your policy chooses the model.

TypeSafe/Jev is optional and requires a TypeSafe credential. It receives the current prompt plus your tier criteria, then returns a tier choice, probabilities, and confidence. It never receives your provider model pool and never selects the exact model.

  1. InputCurrent prompt and tier criteria
  2. JudgmentTier, probabilities, confidence
  3. BoundaryNo provider model pool
  4. SelectionBifrost health filter and strategy

Automatic when useful. Explicit when you know.

Use only as much routing as the task needs. Every control operates on Pi's real active model.

Adaptive

Leave routing on with nothing pinned and Bifrost picks a model for every message through your configured routing policy.

Explicit tier

Start a prompt with a configured tier name, such as quick commit the changes. Bifrost strips the tier name and applies that tier's pool and strategy for one message.

Exact model

Select a model manually or run /bifrost pin. Pin is a session-local hard lock: no automatic routing or tier-prefix parsing.

Predictable under failure. Inspectable by default.

Bifrost changes future routing without silently repeating work that may already have edited files, called tools, or touched external systems.

  • Nativeactivates Pi's actual model
  • Persistentremembers model failures
  • Replay-freenever resends failed work

Preview before generation

/bifrost preview resolves the route without starting generation or activating the model. An enabled classifier may still receive the preview prompt.

Keep cache tradeoffs visible

Per-turn switching can fragment provider prompt-cache locality. Pin for continuity, or read the N-switch cache guide.

Install, probe, review.

Requires Pi 0.86.0 or newer and at least one authenticated provider model visible in Pi. /bifrost init uses a recent probe or tests registry models, then writes only after confirmation.

Primary probe requests use 1+1= with at most 5 output tokens; empty responses may trigger a minimal-session fallback. Provider usage or rate limits may apply. The proposal may enable a prompt classifier, so review it before confirmation.

Three useful answers

Detailed setup and reference material lives in the versioned guide.

Do I need an LLM classifier?

No. A message that starts with a tier name, regex rules, and the configured default may resolve the tier instead. can route without another model call. Prompt classifiers and TypeSafe/Jev are optional when semantic tier judgment adds value.

Does routing affect provider prompt caching?

It can. Treat every provider/model pair as an independent cache history. Returning to a model may reuse its longest still-valid prefix, while newer conversation content remains an uncached tail. Bifrost does not manage provider caches. Read the dedicated A → B → A and N-switch guide.

What happens when a model fails?

Bifrost records the failure, opens a circuit after the configured threshold, and excludes that model from future routes until a controlled recovery trial. It never automatically replays the failed prompt.
